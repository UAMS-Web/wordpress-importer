# History — the host app's current content is not the corpus

The incident history, measurements and worked examples behind [`current-content-is-not-the-corpus.md`](../rules/current-content-is-not-the-corpus.md), moved out of the auto-loaded file unchanged by wordpress-importer-archive#1257. The instructions themselves stay in [`current-content-is-not-the-corpus.md`](../rules/current-content-is-not-the-corpus.md); this file is read when a rule is questioned, not on every turn.

## Overview

**Why this is a standing order.** Observed 2026-08-03 while resolving the [#5](https://github.com/UAMS-Web/wordpress-importer-archive/issues/5) plain-text-password fork. `grep -rl "visibility_password" content/` returned **0**, which was read as "the plain-text fallback in `PasswordVerifier` is dead code — delete it." Two writers had gone uncounted. The importer's `BaseEntryCreator` sets `visibility_password` and `is_password_hashed = true` together in one branch, so *imported* entries are always flagged — but `visibility_password` is also a **CP-editable blueprint field** (via the `uamsweb_common_status` fieldset, on 14+ blueprints), and **nothing in the host app hashes on save** (`grep -rn 'Hash::make' app/` → zero). So every password an editor types in the CP is stored in plain text with the flag unset, and the "dead" fallback is the only thing making those work. Deleting it would have broken exactly the passwords the audit was meant to protect — the recommendation inverted once the writers were enumerated. The zero-result grep was true and led straight to the wrong answer.
